# Свой портал: облако, почта, календарь и Office

[English](README.md) · [Архитектура](docs/ARCHITECTURE.md) · [Эксплуатация / Operations](docs/OPERATIONS.md) · [Опыт внедрения / Lessons](docs/LESSONS.md)

## Быстрый старт: [мастер установки `install.sh`](install.sh)

На **новой чистой VPS**, из root-shell (Git и Python3 должны быть установлены):

```bash
git clone --branch v1.1.0 --depth 1 https://github.com/kaiser1919-ai/mail-cloud-office.git
cd mail-cloud-office
bash install.sh
```

[**v1.1.0 — единый релиз для Ubuntu 24.04 и Debian 13**](https://github.com/kaiser1919-ai/mail-cloud-office/releases/tag/v1.1.0). Один мастер определяет ОС автоматически. Команда устанавливает зафиксированный релиз исходников, а не изменяемую ветку `main`. Прежние релизы по ОС сохранены как исторические снимки.

## Минимальные требования к серверу

- Ubuntu 24.04 LTS **или Debian 13**, amd64, systemd и root. Обе ОС проверены на отдельных чистых VPS для v1.0; обновлённому стеку v1.1 нужна новая серверная приёмка.
- Примерно **2 ГиБ RAM + 4 ГиБ SWAP**; для Office предпочтительно 4+ ГиБ RAM. Если SWAP недостаточно, мастер объяснит назначение и предложит создать недостающий объём с отдельным подтверждением. Имеющийся SWAP не отключается.
- Свободно **размер пула +25 ГиБ** на `/srv` **после подготовки SWAP**: по умолчанию 105 ГиБ для 80 ГиБ raw-пула. При отсутствии подкачки нужно дополнительно до 4 ГиБ на её файл. Ёмкость raw-образа не равна полезной ёмкости ext4.
- Собственный домен, статический публичный IPv4, управление DNS и PTR у провайдера.
- Входящие TCP 80/443/25/587/993, исходящие TCP 25/HTTPS; доступ к штатным репозиториям ОС, GitHub, Nextcloud и ACME. Firewall/SSH автоматически не отключаются.
- **Не существующий сервер с почтой/БД/вебом.** Мастер откажется при чужом стеке, занятых портах или недостаточном резерве.

> **v1.1.0 — обновление исходников до стабильных компонентов, не новая серверная приёмка.** Версии и заявленная совместимость проверены; локальные тесты/CI описаны в [отчёте v1.1](reports/release-1.1.md). Проверки установки, перезагрузки и браузерной работы Mail/Office из v1.0 исторические и не подтверждают новый стек NC35. Перед реальными данными нужны приёмка на чистой VPS, независимый backup и MFA владельца. [Исторический отчёт Debian13](reports/debian-13-acceptance.md).

Одна терминальная команда запускает мастер. Он спрашивает домен, публичный IPv4, контактный email для сертификатов, количество ящиков и их логины, затем устанавливает нативный стек. Отдельный Ansible вручную настраивать не нужно: мастер устанавливает `ansible-core` из штатного репозитория ОС и запускает локальный playbook.

## Что внутри

| Назначение | Компоненты |
|---|---|
| Единый портал | Nextcloud **35.0.2**, Mail **5.13.1**, Calendar **6.6.5** |
| Редактор документов | richdocuments **12.0.1**, встроенный Collabora CODE **26.4.502** в отдельной systemd-службе |
| Общие аккаунты | Локальный OpenLDAP, один email/пароль для облака и ящика |
| Почтовый сервер | Postfix, Dovecot **2.3 (Ubuntu) / 2.4 (Debian)**, Rspamd, DKIM, лимит исходящих **50/час на аккаунт** |
| Исполнение | PHP **8.3 (Ubuntu) / 8.4 (Debian)** FPM, MariaDB, APCu, две отдельные Redis, Nginx, Certbot |
| Хранение | Общий физически зарезервированный ext4-пул, отдельный 2 GiB staging, индикатор реальной ёмкости |

Это не Docker/AIO/Mailcow и не внешний OIDC/SSO. Mail работает в сессии Nextcloud и получает пароль текущего LDAP-пользователя штатным механизмом. Аварийный `recovery_admin` — отдельный локальный администратор, не почтовый ящик.

Версии приложений — официальные стабильные релизы, проверенные **09.11.2026** и зафиксированные в `components.json` с проверенными SHA256 архивов; это не гарантия безопасности навсегда. До публичной эксплуатации проверь актуальную поддержку/security advisories и протестируй обновление. Пакеты ОС при каждом запуске выбирают новейшие доступные кандидаты подписанных штатных stable/security-репозиториев Ubuntu/Debian, не произвольные upstream major-версии; версии записываются в `/srv/mail-cloud/state/packages.tsv`.

**Не команда обновления установленного сервера:** v1.1 откажется до изменения пакетов/служб, если версии существующего ядра или приложений отличаются. Не запускай поверх v1.0. Для повторов/проверок старой установки используй её исходный релиз; миграцию Nextcloud планируй отдельно с backup и тестами. Прерванная установка той же v1.1 возобновляется. Встроенные LDAP/TOTP/backup codes обновляются вместе с ядром; локальный индикатор ёмкости — `sentinel_pool 0.2.0` (метаданные NC34–35).

## Профили ОС — выбираются автоматически

| ОС | PHP/FPM | Dovecot | Фактическая проверка |
|---|---|---|---|
| **Ubuntu 24.04 LTS** | **8.3** | **2.3**, отдельный LDAP-файл и нативные TLS-настройки | v1.0 live PASS; v1.1 только local/CI |
| Debian 13 | 8.4 | 2.4, отдельный шаблон нового синтаксиса | v1.0 live PASS; v1.1 только local/CI |

Мастер сам определяет ОС: дополнительного вопроса нет. На Ubuntu штатно включает **Universe**, если компонент отключён; сторонние PPA не добавляет и дистрибутив не обновляет. PHP 8.3 допускается метаданными зафиксированного Nextcloud 35.0.2. Все PHP-помощники, FPM и cron используют выбранную версию, не случайную системную альтернативу. AppArmor не отключается: для LDAP добавляются локальные разрешения на проектные пути, а для CODE AppImage — адресное разрешение user namespaces без глобальной смены sysctl. В приёмке v1.0 адресные профили загружены на настоящем ядре тестовой VPS, Office успешно исполнялся; глобального отключения AppArmor нет. Смена ОС/профиля при возобновлении блокируется — это не механизм миграции Debian→Ubuntu.

## Параметры мастера

Запускай в root-shell. Мастер спросит домен, IPv4, email ACME, **количество ящиков (1–20)** и **логин каждого**. Затем попросит `INSTALL`; если нужен новый SWAP, отдельно спросит `CREATE SWAP`. Это подтверждения действий, не запрос пароля.

По домену `example.org` выводятся имена `disk.example.org` и `mail.example.org`. Логин каждого ящика вводится отдельно: например, `alice`, затем `bob` (не полный email). Адреса входа будут `alice@example.org`, `bob@example.org`. Пароли генерируются криптографически; повторный запуск их не меняет. Только root может прочитать `/etc/mail-cloud-installer/config.json` (0700 каталог, 0600 файл). Мастер явно выводит для каждого адреса путь и JSON-ключ: например, `alice@example.org -> /etc/mail-cloud-installer/config.json : passwords["alice"]`. Сами пароли не печатаются. **Не публикуй и не присылай этот файл.**

Расширенные параметры — JSON, не исполняемый shell-файл:

```bash
cp example.json my-parameters.json
# Замени example.org, IPv4, email и пользователей своими значениями.
# При необходимости задай cloud_host, mail_host, pool_gib.
bash install.sh --plan --config my-parameters.json  # без root, сети и изменений
bash install.sh --config my-parameters.json         # root, установка
```

`--plan` проверяет ввод, но не проверяет состояние VPS. Не загружай случайный JSON с паролями; принимаются только перечисленные открытые параметры.

## DNS и точки остановки

Мастер показывает точные записи для твоего домена и ключа:

- A для `disk` и `mail`, MX домена на `mail`.
- SPF с единственным IPv4 отправки, DKIM `mc._domainkey` с **реальным новым** ключом, DMARC `p=none`.
- PTR IPv4 → `mail.DOMAIN` у провайдера.

Не ставь SPF `-all`, если у домена есть другие отправители: сначала согласуй политику. Для сложной существующей почты этот установщик не предназначен. Не используй HTTP/CDN-прокси для почтового hostname. AAAA должен отсутствовать: внешний почтовый стек здесь рассчитан на IPv4.

Если устанавливаешь на поддомен `test.example.org`, а DNS-зона называется `example.org`, имя DKIM-записи в этой зоне будет `mc._domainkey.test` (полное имя — `mc._domainkey.test.example.org`). Это запись **тестового поддомена**, не основной почты. После переустановки сервера замени старое значение этой записи новым ключом мастера; не создавай вторую TXT-запись с тем же именем и не меняй MX/SPF/DKIM основного домена.

Без API-доступа к твоему регистратору/хостеру скрипт не может править их DNS/PTR. При несовпадении он остановится, сохранив параметры; исправь записи, дождись распространения и запусти ту же команду. Никаких новых паролей и повторного форматирования не произойдёт. До DNS/конфигурационной приёмки почтовые службы замаскированы; это сохраняется при перезагрузке.

HTTPS выпускается автоматически через HTTP-01 на 80 порту; самоподписанной подмены при ошибке нет. Почта не включается до полной DNS-проверки. Успешный DNS-тест **не доказывает** доступность внешнего TCP25 и доставляемость.

## Первый вход и открытие портала

По умолчанию портал доступен только через localhost. Сначала настрой TOTP и резервные коды `recovery_admin` через защищённый SSH-туннель, затем:

```bash
bash install.sh --open-portal
bash install.sh --check
```

`--open-portal` проверяет, что TOTP и backup codes включены, и только затем снимает localhost-ограничение. Настройка телефона/MFA не может быть безопасно выполнена скриптом вместо владельца. Конкретный туннель/сопоставление hostname: [OPERATIONS](docs/OPERATIONS.md).

## Чего здесь нет

Нет переноса чужих файлов/ящиков, сайта, VPN, ботов, платных сервисов и внешнего backup. Нет автоматического безнадзорного обновления Nextcloud/apps, DNS API или гарантии репутации IP. Локальная установка и копия конфигов — **не резервная копия**.

Зелёные unit tests не заменяют настоящую машину. Дополнительная операторская проверка перед production (не подменяется результатами ограниченной тестовой VPS): install → rerun → reboot; две отдельные браузерные сессии, почта туда/обратно с внешним провайдером, приватность файлов/ящиков, отрицательный relay/sender/auth, Office create/edit/save/reopen/export, проверка отказа при потере mount и восстановление backup на отдельной машине.

## Разработка

Для разработки Ansible2.22 нужен **Python3.13+** (CI3.13/3.14); ниже запускай `python3` соответствующей версии. На VPS мастер использует штатные Ansible/Python своей ОС, не этот dev-pin.

```bash
python3 -m venv .venv
.venv/bin/pip install 'ansible-core==2.22.0' jinja2 pyyaml
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/ansible-playbook -i localhost, -c local ansible/site.yml --syntax-check
```

CI проверяет обе ветки шаблонов и Python 3.12/3.13; отдельный изолированный Ubuntu 24.04 контейнер устанавливает настоящие пакеты, проверяет парсеры и синтетические LDAP/IMAPS/LMTP/Redis-сценарии. Это **не полная установка VPS**, не systemd/reboot/публичный SMTP/Office-приёмка. Docker используется только как оболочка CI, не как способ установки продукта. Лицензия исходников AGPL-3.0-only; приложения и Debian-пакеты сохраняют свои upstream-лицензии. Проприетарных шрифтов и личных credentials в репозитории нет.

### Ограниченный тест на диске с малым запасом
Только на отдельной тестовой VPS и после явного согласования риска:
`sudo ./install.sh --test-low-headroom --config /root/test-parameters.json`.
Нужны размер образа +8 ГиБ свободного места вместо обычных +25; флаг обязателен
при каждом повторном запуске. Режим не меняется задним числом. Перед/после фаз
проверяются 2 ГиБ свободного пространства **вне** образов, 250 МиБ MemAvailable
и 512 МиБ SwapFree; при нехватке установка останавливается без удаления данных.
Скачивание/распаковка также сохраняют системный резерв 2 ГиБ.
После установки: `sudo python3 tests/stress_pool.py --confirm-test-vps --gib 2`,
затем при необходимости `--gib 80`: запись ограничена фактическим свободным
местом пула с резервом 1 ГиБ, проверкой SHA256 при чтении и очисткой только
собственной временной папки. Это файловый стресс-тест, не замена проверки
параллельной работы Nextcloud/почты/Office. При аварийном SIGKILL fixture может
остаться: проверить вручную, мастер не удаляет неизвестные файлы автоматически.
80 ГиБ — физический размер ext4-образа; фактическая ёмкость меньше из-за
метаданных ext4. Индикатор показывает реальную ёмкость, а не обещанные 80 ГиБ.
Это не рекомендуемый производственный режим и не гарантия, что весь стек
поместится на любом диске 100 ГБ.

Для отдельной тестовой VPS с минимум двумя тестовыми пользователями:
`sudo python3 tests/cloud_acceptance.py --confirm-test-vps` проверяет WebDAV
write/read, запрет чужого файла и неверного/чужого пароля, затем удаляет только
свои UUID-fixtures с per-request skip-trash (не очищает корзины пользователей).
Пароли берутся из root-private state только в память, HTTPS проверяется;
публичное открытие портала/MFA для локального теста не требуется.
Это не заменяет браузерную проверку входа, Mail/Office и reboot.
